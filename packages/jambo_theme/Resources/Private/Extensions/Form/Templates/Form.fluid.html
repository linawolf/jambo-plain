Copy of the template of EXT:form with a summary of the errors in front of the form: one place that says what went wrong, which is the pattern a visitor using a screen reader expects, and the only place where the error of a hidden element - the submission guard - can be read at all. The summary walks the elements of the page instead of the flattened errors of the form, because that is the only way to reach formvh:translateElementError: printing an {error} straight from the validation results gives the untranslated Extbase default ("The given subject was empty"), which names neither the field nor what to do. Both forms here have a single page.

  • A hidden field: a link would send the visitor to something they can neither see nor fix. {formvh:translateElementError(element: element, error: error)} {formvh:translateElementError(element: element, error: error)}
    • An error can belong to no element of the page: the honeypot is built fresh on every render, so when it trips, its error points at a field name that no longer exists. Without this the visitor would get an empty "There is a problem" box - and a honeypot does trip on a real person now and then, when the browser autofills a field it cannot see.
